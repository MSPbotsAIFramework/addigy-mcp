## Product design

### Goals / Non-goals

**Goals**: Addigy V2 is connectable as an MCP vendor through the MSPbots gateway — a user can enter an Addigy API Key, the 5 scoped tools (device, alert, policy, installed-app queries) become callable by any connected AI client, and every call is encrypted in transit/at rest for the credential and recorded in the connector's audit log.

**Non-goals**: the legacy, non-V2 "Addigy" integration (Site + Client ID + Client Secret auth, per `addigy-mcp/README.md`'s own naming note) is out of scope — this ticket is V2 only, matching the existing repo's scope decision. Expanding beyond the 5 scoped interfaces to the full Addigy API surface (300+ endpoints per the README's "Known Gaps") is out of scope. New credential types or multi-key auth are out of scope — the shape is fixed to the single API Key the repo and the gateway middleware already agree on.

### Acceptance criteria AC1..AC6

- **AC1**: Given the Addigy V2 MCP server is registered with the gateway, when an admin opens Capabilities → Library, then "Addigy" (V2) appears as connectable, and `GET /admin/integrations` lists an `addigy` entry whose credential fields include `api_key`.
- **AC2**: Given a tenant enters an Addigy API Key in the Connect dialog, when the key is invalid, then the save is rejected (HTTP 422) with a message referencing the API Key field (not raw credential leakage); when the key is valid, then the save succeeds and the tenant's credential list includes `addigy`.
- **AC3**: Given a tenant has connected Addigy with a valid key, when they open the connector's Tools list, then it shows all 5 tools (`addigy_query_devices`, `addigy_get_alerts`, `addigy_query_policies`, `addigy_query_installed_apps_agent`, `addigy_query_installed_apps_mdm`) — Tools count > 0.
- **AC4**: Given a connected tenant, when an agent asks a question that maps to one of the 5 tools (e.g., "what policies exist for this org?"), then the agent calls the tool through the gateway and returns a real, non-error result from Addigy.
- **AC5**: Given a tool call has been made, when the tenant opens the connector's audit/activity log, then the call appears (who, which vendor, when) and the API Key never appears in plain text anywhere in that log.
- **AC6**: Given a tenant disconnects Addigy, when they check the connection afterward, then the stored credential is gone and fetching connection info returns 404 / prompts reconnect; separately, a direct call to the MCP server missing the `X-Addigy-Api-Key` header returns 401.

### Open questions

- **Is `addigy` currently registered and enabled in the live `mcpm_vendor_registry` / `mcpm_integrations` tables (INT and/or prod)?** Not visible from git (registration moved to a DB table on 2026-09-07; see Current state). **Non-blocking** — assumption: the dev leg checks this directly (`scripts/vendor_deploy.py status` or `GET /admin/integrations`) at dev time and registers/deploys via the existing playbook if missing, exactly as Leo Yang's comment on this ticket anticipates ("if the repo already exists, publish to INT directly"). If assumption is wrong (i.e., registration requires a code or schema change), the dev leg should treat that as a gateway change and hand off per `references/mcp-track.md` §6, not attempt it itself.
- **Is the API key embedded in `mcp-service-gateway`'s `test/src/addigy_test.py` still a live, valid Addigy V2 credential?** Non-blocking — assumption: the dev leg verifies it still authenticates before relying on it for AC2-AC5 evidence; if it has been rotated/revoked, this ticket falls back to the PRD-21194 pattern (no code is blocked, only the self-test evidence is deferred — not a "code" blocker, see Risks).

## Tech design

### Conclusion

Ready to code: yes. No new source files are expected in either repo: `addigy-mcp` is already a complete, SOP-compliant 5-tool implementation, and the gateway-side credential middleware and an existing end-to-end lifecycle test already exist and are correct. The remaining work is operational, not code: confirm `addigy` is registered and deployed in the live vendor registry/gateway; if not, register + deploy it via the existing `scripts/vendor_deploy.py` playbook (the same one used for all 100+ other vendors in that table); then run the existing `test/src/addigy_test.py` suite (or the equivalent manual Capabilities-UI walkthrough) as self-test evidence for AC1-AC6. Unlike the epic's own precedent PRD-21194 (Action1), which stalled because no real vendor trial account was available, this ticket already has a usable Addigy V2 test credential committed in `test/src/addigy_test.py`, so the dev leg should not need to source a new vendor account to prove the full round trip.

### Where the current implementation lives

- `MSPbotsAIFramework/addigy-mcp@main (018e53e)` — full tree, see Current state.
- `MSPbotsAIFramework/mcp-service-gateway@main (67013d8)` — read-only reference: `mcp-manager/mcp_manager/auth/credentials/addigy.py`, `test/src/addigy_test.py`, `scripts/vendor_deploy.py`, `document/vendor-registry-db-migration.md`.

### Option analysis

Only one viable path: reuse the existing, already-SOP-compliant `addigy-mcp` implementation and the existing gateway registration/deploy tooling. Writing a new `addigy-mcp` server from scratch was considered and rejected — the current repo already satisfies the ticket's ask end-to-end (credential shape, tool scope, SOP error/retry/instructions conventions), and duplicating it would violate reuse-first and produce two servers for one vendor.

### Change list

None expected in source code of either repo. If the dev leg finds `addigy` missing from `mcpm_vendor_registry`, the change is a registry entry (via the admin-console UI or `scripts/vendor_deploy.py register`), which is data, not gateway source code, and is not a "gateway change" under `references/mcp-track.md` §2.3/§6.

### Reuse & cleanup

- **Reuse**: 100% of `addigy-mcp`'s existing implementation and `mcp-service-gateway`'s existing `AddigyCredentialMiddleware` and `test/src/addigy_test.py`. No new dependencies.
- **API/param shape**: unchanged — see README's Tool List table, already implemented.
- **In-scope cleanup**: none. The repo already received its SOP-compliance pass (commit 07a2302) and the README has no stale content to correct.
- **Follow-ups (out of scope, flag only)**: `test/src/addigy_test.py` embeds a plaintext-looking Addigy V2 API key committed to the gateway repo. This predates this ticket, is not caused by it, and is a secrets-hygiene concern for whoever owns `mcp-service-gateway`'s secrets (same category as the previously-flagged committed `.github_token` on PRD-21194) — worth a follow-up ticket, not a fix here.

### Data & API contract

Unchanged. Single credential header `X-Addigy-Api-Key` (gateway middleware maps the submitted `api_key` form field to it); 5 read-only tools against `https://api.addigy.com/api/v2` as documented in `addigy-mcp/README.md`'s Tool List table and implemented in `src/addigy_mcp/tools/{devices,alerts,policies,apps}.py`.

### Key flow / sequence

Matches `test/src/addigy_test.py:run_all` (gateway repo, read-only reference): health check → confirm `addigy` registered with `api_key` field → reject a wrong key (422) → write a real tenant credential → confirm tenant credential list includes `addigy` → confirm tenant-visible integrations list includes `addigy` → fetch connection info (validate gateway URL + bearer token shape) → real MCP connect + `addigy_query_policies` tool call through the gateway → delete tenant credential → confirm credential removed and connection info now 404s.

### Non-functional

- **Credential security**: encrypted per-record (gateway-wide AES-256-GCM, per SOP), already implemented — no new work. The server itself never persists the API key (`server.py` holds it only in a per-request `contextvars.ContextVar`, reset after each request — `server.py:16-18,65-69`).
- **Multi-tenant isolation**: `test/src/addigy_test.py` scopes its credential write/read/delete to a dedicated `TENANT_CODE` and never mutates the global `addigy` integration definition (`:1-11`), matching the existing per-tenant credential isolation pattern used for every other vendor.
- **Concurrency**: per-request isolation is via `contextvars`, which asyncio copies per task, so concurrent SSE connections from different tenants do not leak credentials into each other (`server.py:13-18`) — already implemented, not new.
- **Observability**: covered generically by the gateway's existing audit log (AC5); no connector-specific logging work needed.

### Rollout & rollback

Rollout: publish via the existing `scripts/vendor_deploy.py` / admin-console path — the same mechanism already used for the other 100+ vendors in `mcpm_vendor_registry`. Rollback: admin-console Offboard, or `scripts/vendor_deploy.py down --name addigy`, scoped to this one vendor with no shared-state impact (per `document/vendor-registry-db-migration.md` §5, deleting one vendor's registry row has no effect on others).

### Test strategy

Primary: run the existing `test/src/addigy_test.py` suite end-to-end as self-test evidence (it already encodes TC1-TC7 below). Supplement with a manual Capabilities-UI walkthrough for AC1/AC3/AC4/AC5 if the dev leg prefers UI-level evidence over the API-level test script, mirroring the acceptance steps the BA already used on the sibling ticket PRD-21194.

### Effort & breakdown

Operational only: 0 engineering-days of code change expected. ~0.5 day to verify registration status, register + deploy if missing, and run self-test. Near-zero if `addigy` turns out to already be registered and deployed (then it's confirm + publish only, matching Leo Yang's comment).

### Risks & dependencies

- Depends on INT/registry write access and, if `addigy` is not yet registered, a working `GITHUB_TOKEN` for `vendor_deploy.py`'s build step — the same class of access the epic's precedent (PRD-21194) found itself missing. Unlike PRD-21194, a usable test credential already exists in-repo, so the vendor-trial-account gap that stalled PRD-21194 should not recur here; if the dev leg finds the embedded test key has been rotated, that alone is not a code blocker (see Open questions).
- Whether this connector's docs.mspbots.ai wiki page exists/needs updating is handled by the review leg after INT publish (`references/mcp-track.md` §4.5), independent of this design.
